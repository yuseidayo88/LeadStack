# 架電用の電話番号調査

2026-10-07。既存の企業検索・公式サイト補完を拡張したローカル実装。本番未反映。

## 操作

1. 「企業を探す」で県・業種・規模を指定して企業候補を取得する。
2. 一覧で候補を選び、「電話番号を調べる」を押す。10社を超える選択では、ボタンに明示された先頭10社のみが対象。
3. 対象企業を確認して開始する。1社ずつ調べ、進捗・取得失敗・公式URLなし・電話番号なしを表示する。
4. 電話番号候補の出典を開き、社名・所在地・代表電話を確認する。確認欄を選び「電話番号を保存」を押す。
5. 「電話番号ありのN社を取り込む」で既存の重複確認・営業リスト取込へ進む。既存CRMの電話番号は上書きしない。

一覧の「電話番号ありを表示」は、候補に保存された電話番号で絞り込む。未確認の抽出候補を架電可能として扱わない。公式URLがない場合は企業詳細から確認済みURLを入力する。公式サイトを特定する検索API、網羅的なサイト探索、有料データ購入は追加していない。

## 費用と取得量

- 有料検索API・AI API・データ購入・新サービスの追加なし。既存gBizINFOと登録済み公式サイトのみ。
- 一括操作は最大10社、常に1社ずつ。1組織1時間20回の既存DB制限を維持する。個別確認とも共通の枠。
- 保存済み電話番号、CRMの電話番号、公式URLなし、24時間以内の調査結果はサーバーで判定し、サイト取得を省略。成功だけでなく「見つからない」「自動取得不可」も再利用する。
- 再確認が必要な場合は企業詳細で個別に実行する。この場合も同じ回数制限が適用される。
- 各社最大8秒、各応答1MiB、robots.txtと最大2HTMLページ、最大2転送の既存制限を維持。公開IP・転送先検証、robotsの取得拒否等を尊重する。
- 調査画面に新規サイト調査数・結果再利用数・電話候補数・電話番号あり件数・実測所要秒数を表示。所要時間はブラウザーでの経過時間であり、サーバーCPU時間や請求額ではない。
- サーバー処理・通信・保存容量は消費する。既存契約枠内かどうかは本番の利用量で確認が必要であり、追加請求0円は保証しない。

## 中断・整合性

- 開始直後に「調査中…」を表示し、二重開始を防止する。
- 停止すると実行中の1社の応答・保存を待って終了し、次の企業へ進まない。表示は「停止中…」と「停止しました」を区別する。
- 画面離脱・組織切替後も新しい企業へのリクエストを開始しない。すでに開始した1社は結果保存まで進む場合がある。永続キューや自動再開は作らない。
- 時間切れ・通信エラー・権限エラー・取得上限では後続を中断し、自動リトライしない。取得済み結果はDBに残り、再読込後も再利用できる。
- 公式URL変更時の証拠破棄、取得・保存時の `updated_at` による競合検出を維持する。1分未満の進行中調査は重複実行せず、残留した進行中状態は再調査可能。
- 電話番号の確定APIは明示確認を必須にし、DB内の補完結果を採用する。クライアントから番号・出典・従業員数を指定できず、既存番号を上書きしない。
- 社名・所在地の一致と番号の用途は利用者が出典を確認する。自動取得がその企業の代表番号であることを保証するものではない。

## 実装と検証

既存の組織認可、候補RLS、補完処理、回数制限、重複確認・CRM取込を使用する。DBマイグレーション・環境変数・依存関係の追加は不要。

`research_phone` と `confirm_phone` を既存の `/api/organizations/[org]/company-discovery` に追加。読み取り専用メンバーによる実行を拒否し、すべての候補アクセスに組織IDを指定する。

```sh
npm test
npm run lint
npm run typecheck
npm run build
# 独立ローカルAuth/PostgREST + 合成サイト用preloadで起動したアプリのみ

```

`phone-research-preload.mjs` は明示的に有効化したローカルNextプロセスでのみ合成HTMLを返し、外部DNS/HTTP/fetchを遮断する。実サイトの電話取得率と、本番での処理・通信使用量はこのテストでは測定しない。
